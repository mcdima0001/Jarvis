# Архитектура Jarvis

Документ для будущего себя: **почему** сделано именно так. Код показывает «как»,
здесь — обоснования, чтобы через год не переделать по кругу.

## Главная цель

1. Новая возможность = файл в `skills/`. Без правки ядра, без регистрации, без конфига.
2. Любая часть (LLM, STT, TTS, память, шина, роутер) заменяется без переписывания
   остального.

Всё ниже подчинено этим двум пунктам.

---

## 1. Два канала связи, а не один

**Общепринятая идея:** «все модули общаются только через события».

**Почему её мало.** Событие — это факт, отправленный в никуда: у него может быть
сколько угодно подписчиков и нет возвращаемого значения. Но «какая температура»
требует ответа здесь и сейчас. На чистом pub/sub это решается correlation-id,
событиями-ответами и таймаутами — и через год половина кода будет этой обвязкой.

**Решение — два канала:**

| | EventBus | ToolRegistry |
|---|---|---|
| Смысл | факт о мире | команда |
| Направление | 1 → N подписчиков | 1 → 1 обработчик |
| Результат | нет | `ToolResult`, через `await` |
| Пример | `sensor.temperature.changed` | `esp32.get_temperature()` |

Развязка сохраняется полностью: скилл вызывает чужой инструмент **по строковому
имени**, а не импортом.

```python
# Правильно: связь по имени, реализация неизвестна
await self.tools.invoke("windows.launch_program", {"program": "obs"})

# Запрещено: жёсткая связь между скиллами
from skills.windows.skill import WindowsSkill
```

Правило «скилл не импортирует скилл» железное. Аналогия: события — это
уведомления, инструменты — RPC. Оба развязаны по имени, но второй возвращает
значение.

## 2. Роутер отдаёт намерение, а не скилл

**Общепринятая идея:** роутер определяет, какой скилл обработает запрос.

**Почему это тупик.** Function-calling у LLM возвращает *имя функции и аргументы*,
а не скилл. Если роутер мыслит скиллами, слой LLM придётся переводить туда-обратно.

**Решение:** `Router: str → Intent(tool="esp32.set_mode", args={"mode": "game"})`.
Кто владеет инструментом — забота реестра, роутер об этом не знает.

Роутер — цепочка резолверов, каждый возвращает `Intent | None`:

| # | Резолвер | Что делает | Цена |
|---|---|---|---|
| 1 | `phrase` | точные фразы и шаблоны из объявлений скиллов | 0 токенов |
| 2 | `alias` | синонимы из конфига, нечёткое сравнение | 0 токенов |
| 3 | `llm` | function-calling по каталогу инструментов | вызов API |
| 4 | `fallback` | свободный диалог | вызов API |

Порядок и порог — в конфиге. Отсюда прямо следует экономия: типовые команды
студии («включи игровой режим», «какая температура») до сети не доходят.

Скилл объявляет фразы сам, поэтому **новый скилл расширяет маршрутизацию
автоматически**.

**Тонкость, найденная тестами.** Порог уверенности нужен, чтобы слабая догадка не
обошла более сильный резолвер дальше по цепочке. Но за последним звеном никого
нет — применять порог там значит просто терять запрос. Поэтому результат
последнего резолвера принимается всегда (`router.py`).

## 3. Провайдер LLM тонкий, задачи — уровнем выше

**Общепринятая идея:** `LLMProvider` с методами `ask/chat/summarize/extract_intent`,
реализуемый `OpenRouterProvider`.

**Почему это ломает собственную цель.** `summarize()` — это промпт и постобработка,
а не особенность провайдера. Положив его в интерфейс, обязываешь каждый новый
провайдер (Gemini, Groq, DeepSeek) переписывать одну и ту же логику. Пять
провайдеров — пять копий одного промпта.

**Решение — два слоя:**

* `LLMProvider` — только транспорт: `complete(LLMRequest) -> LLMResponse`.
  **Новый провайдер = один метод.**
* `LLMService` — `ask`, `chat`, `summarize`, `extract_intent`. Написан один раз.

**Профили задач** закрывают оба требования — разные модели под разные задачи и
смена на лету — одним механизмом:

```yaml
llm:
  profiles:
    dialog:    {provider: openrouter, model: anthropic/claude-sonnet-5}
    code:      {provider: openrouter, model: anthropic/claude-opus-5}
    intent:    {provider: openrouter, model: anthropic/claude-haiku-4-5}
```

```python
llm.set_model("code", "другая/модель")   # в рантайме, без перезапуска
```

Дешёвая модель на разбор команд, сильная на код — экономия без потери качества
там, где оно важно.

## 4. Whisper и Piper заблокировали бы всё приложение

Требование «не использовать блокирующий код» само по себе не выполняется
объявлением метода `async`. `faster-whisper` и Piper синхронные и CPU-bound:
вызов внутри корутины замораживает event loop целиком — подписки, таймеры, сеть.

Поэтому в архитектуре есть явный контракт: **тяжёлый адаптер ходит только через
`BlockingWorker`** (`core/runtime/worker.py`) — выделенный пул потоков с
ограниченной очередью. Это не деталь реализации, а правило.

## 5. VAD и wake word: место оставлено сразу

В исходном ТЗ их не было. Без них ассистент гоняет Whisper на любом шуме студии:
постоянная нагрузка на CPU и ложные срабатывания.

Полный конвейер:

```
AudioSource → VAD → WakeWord → STT → Router → Dispatcher → (Skill|LLM) → TTS → AudioSink
```

Сейчас на местах VAD и wake word стоят пропускающие заглушки. Silero или
openWakeWord встанут одним классом. Если бы места не оставили, позже они влезли
бы костылём в середину конвейера.

## 6. Память: два типа хранилищ

Разделы из ТЗ (`profile`, `preferences`, `studio`, `today`, `history`…) разной
природы:

* `profile`, `preferences`, `studio`, `projects`, `knowledge` — **документы**:
  читают, правят, пишут обратно.
* `today`, `history` — **журналы**: только дописывают, читают по времени.

Один интерфейс на оба дал бы либо неэффективный журнал, либо неудобный документ.
Поэтому `DocumentStore` (JSON) и `JournalStore` (JSONL) разведены.

Требование «никогда не отправлять всю память в LLM» реализовано не соглашением, а
формой API: у `ContextBuilder` **нет метода «дай всё»** — разделы называются явно
и результат режется по бюджету токенов.

```python
context = await memory.context.build(
    documents=("profile", "studio"),
    journals=("today",),
)
```

## 7. Слой контрактов как точка стабильности

`core/contracts/` — события, `Intent`, `ToolResult`, `Utterance`. От него зависят
все, он не зависит ни от кого. Скиллы импортируют контракты, а не реализации.

Это и есть шов, по которому позже вырезается любая часть: заменить
`LocalEventBus` на Redis или NATS можно, не тронув ни одного скилла.

Имена событий — с пространством имён: `voice.command.recognized`,
`sensor.temperature.changed`, `studio.mode.changed`.

## 8. Изоляция сбоев

Один кривой скилл не должен ронять ядро:

* ошибка обработчика события ловится и логируется, остальные подписчики работают;
* исключение в инструменте возвращается как `ToolResult(ok=False)`, а не всплывает;
* на вызов инструмента есть таймаут (`runtime.tool_timeout`);
* сбойный скилл пропускается при загрузке, остальные грузятся;
* фоновые задачи скилла отменяются вместе с ним.

Всё это держится на `SkillScope`: подписки, инструменты и задачи регистрируются
через него, поэтому выгрузка — это один вызов `revoke()`.

## 9. Hot reload: задел, а не обещание

`SkillManager.reload(name)` работает уже сейчас: отозвать scope → переимпортировать
модуль → создать заново. Файлового watcher'а нет намеренно — он добавляется
поверх готового `reload()` десятком строк, когда понадобится.

**Грабли, которые тест поймал.** Штатный `spec.loader.exec_module` использует
кеш байткода, а заголовок `.pyc` хранит время правки с точностью до секунды.
Файл, переписанный в ту же секунду без изменения размера, считается неизменным —
и перезагрузка молча поднимает **старый** код. Для плагинов, которые правят и
тут же перезагружают, это неприемлемо, поэтому исходник читается и компилируется
вручную (`skills/loader.py`).

## 10. Секреты и конфигурация

Все настройки в `config/config.yaml`; в коде нет ни одного пути и ни одного ключа.
Но ключ API в конфиге, лежащем в git, однажды утечёт, поэтому:

```yaml
api_key: ${JARVIS_OPENROUTER_KEY:-}
```

Значения берутся из окружения и `.env` (в `.gitignore`). Синтаксис `${VAR:-default}`
позволяет системе стартовать без секретов — с заглушками и предупреждением в логе.

Конфиг разбирается один раз в типизированные датаклассы: опечатка ловится при
старте, а не через час работы в глубине скилла.

## 11. Dependency Injection без фреймворка

Ни глобальных переменных, ни синглтонов, ни service locator. Всё собирается в
одном месте — `core/app.py` (composition root) — и передаётся через конструкторы.

Скилл получает всё нужное одним объектом `SkillContext`: конфиг своей секции,
логгер со своим именем, шину, реестр, память, LLM, TTS и scope. Подменить
реализацию в тестах — значит передать другой объект.

## 12. Структура: пакет вместо плоских папок

Код — в пакете `jarvis/`, данные и пользовательский контент — в корне
(`skills/`, `config/`, `memory/`, `models/`, `logs/`). Плоская раскладка
(`core/`, `utils/` в корне) даёт неимпортируемый проект и риск конфликта имён.

Скиллы **намеренно снаружи пакета** и грузятся по пути файла: это плагины, а не
часть ядра.
